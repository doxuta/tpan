## 1. Mốc này làm được gì

- Mỗi site có một user Linux riêng (PHP của site chạy dưới user đó). Sau F1, số UID của user ấy là số chưa từng cấp cho site nào, kể cả site đã xoá hẳn. Số nằm trong dải 65536 đến 99999, tăng dần.
- Xoá hẳn một site (`tpan trash purge`) không còn để lại gì chạy dưới quyền user cũ: crontab bị gỡ, tiến trình còn sống bị giết, file của user ở `/tmp`, `/var/tmp`, `/dev/shm` bị xoá, rồi mới xoá user.
- Trước F1, site tạo kế tiếp nhận lại đúng UID của site vừa xoá, và file sót lại của site cũ (đặc biệt là file setuid) thành file của site mới.
- Kết quả e2e F1: bản chưa vá 80 khẳng định đạt, 6 không đạt (đúng các lỗ); bản vá 86 đạt, 0 không đạt (số của phần nginx, cả hai log).

## 3. Đi qua mã theo thứ tự chạy

Người dùng gõ `tpan site add x2.example.com ...`. Tạo site dựng một danh sách Step (Step là một việc có ba hàm `Check`, `Apply`, `Undo`; xem `13-m13-nhieu-nguoi-dung.md` và các file mốc trước). Danh sách bắt đầu bằng user của site.

### 3.1 `internal/core/site.go` dòng 623: đưa nơi cấp số vào Step

```go
ss := []engine.Step{&steps.SiteUser{Layout: l, UIDs: uids}}
```

`uids` là `*store.Store` (nối với `tpan.db`). `SiteUser` không biết SQLite; nó chỉ cần thứ có hàm `ReserveSiteUID`, nên khai một interface nhỏ `UIDReserver` ở `internal/steps/site_user.go` dòng 130. Nếu `UIDs` là `nil`, `Apply` báo lỗi chứ không để `useradd` tự chọn số (`pickUID`, dòng 208 đến 210): quay về cách cũ chính là cái lỗ.

### 3.2 `internal/steps/site_user.go`, `SiteUser.Apply` (dòng 333 đến 374)

Thứ tự việc:

1. `userLookup`: user tên `tp_<slug>` đã có chưa (`getent passwd`). Có rồi và đúng home, shell thì xong, không đổi gì. Đây là lý do site cũ giữ UID cũ.
2. `userGroupID` (dòng 298): chọn số. Nếu có sẵn nhóm cùng tên với GID trong dải thì dùng lại số đó (lần chạy trước bị ngắt giữa `groupadd` và `useradd`). Không thì gọi `pickUID`.
3. `groupadd --gid N tp_...`, rồi `useradd --system --uid N --gid N ...`.
4. `useradd` lỗi thì chạy `groupdel` để không để nhóm mồ côi (dòng 367). Số N đã ghi trong `tpan.db` nên lần chạy lại lấy số mới; bỏ phí một số, không sao.

Lệnh thật (dòng 158 đến 178):

```go
func (s *SiteUser) groupadd(id string) system.Cmd {
	return system.Cmd{Name: "groupadd", Args: []string{"--gid", id, s.Layout.User}}
}
...
return system.Cmd{Name: "useradd", Args: []string{
	"--system", "--uid", id, "--gid", id,
	"--home-dir", l.Dir, "--no-create-home",
	"--shell", userShell,
	l.User,
}}
```

Lệnh chạy bằng danh sách đối số (argv) qua `system.System`, không qua `sh -c` (luật cứng số 3 của repo).

### 3.3 `pickUID` (dòng 207 đến 249): chọn số

Ba lớp:

```go
floor := siteUIDMin
for _, p := range []string{"/etc/passwd", "/etc/group"} {
	... // mỗi dòng: trường thứ ba là UID hay GID; nếu nằm trong dải thì floor = id + 1
}
for range siteUIDTries {
	n, err := s.UIDs.ReserveSiteUID(ctx, floor)
	...
	taken, err := idTaken(ctx, sys, n)
	if !taken { return n, nil }
	floor = n + 1
}
```

- `floor`: sàn. Bắt đầu 65536 và nhảy lên trên mọi UID, GID đang có trong `/etc/passwd`, `/etc/group` mà nằm trong dải. Phòng máy đã có user lạ ở đó, hay `tpan.db` mới trên máy cũ.
- `ReserveSiteUID(floor)`: số lớn nhất từng cấp cộng 1, hay `floor` nếu lớn hơn. Mục 3.4.
- `idTaken`: hỏi `getent passwd N` và `getent group N`. `getent` hỏi qua NSS, tức cả các nguồn khác file (LDAP chẳng hạn). Nếu số đã có người dùng thì thử số kế tiếp, tối đa `siteUIDTries = 100` lần.
- `n > siteUIDMax` (99999) thì báo "hết dải" rõ ràng. 34464 số (`99999 - 65536 + 1`) cho cả đời máy; mã ghi đây là chỗ đã chấp nhận hạn chế (chú thích `ponytail:`) và đường nâng cấp là đọc `/etc/subuid` để biết chỗ trống phía trên.

### 3.4 `internal/store/site_uid.go`, `ReserveSiteUID`: số ghi trước khi chạy lệnh

```go
`INSERT INTO settings (key, value, updated_at) VALUES (?, ?, ?)
 ON CONFLICT (key) DO UPDATE SET
   value = CAST(MAX(CAST(settings.value AS INTEGER) + 1, CAST(excluded.value AS INTEGER)) AS TEXT),
   updated_at = excluded.updated_at
 RETURNING value`
```

Một câu SQL làm cả ba việc: nếu khoá `site_uid_max` chưa có thì ghi `floor`; nếu có thì lấy lớn hơn giữa "số cũ + 1" và `floor`; rồi trả về số vừa ghi (`RETURNING`). Vì chỉ một câu lệnh, panel và CLI chạy cùng lúc trên cùng `tpan.db` vẫn nhận hai số khác nhau (comment trong file nói vậy; mình chưa chạy phép thử đua nhau để kiểm).

Thứ tự là điểm mấu chốt: `ReserveSiteUID` chạy TRƯỚC `useradd`. Hai khả năng khi tiến trình chết giữa chừng:

- ghi xong, `useradd` chưa chạy: bỏ phí một số. Vô hại.
- `useradd` xong mà chưa kịp ghi: số có thể cấp lại. Đây là khả năng cần tránh, và thứ tự "ghi trước" loại nó.

Không cần bảng hay migration mới: một dòng trong bảng `settings` (khoá `site_uid_max`, hằng `SiteUIDKey`).

`SiteUser.Info` (dòng 189) hiển thị bản xem trước với chữ `<UID>` thay cho số (`uidPlaceholder`), để xem trước (`--dry-run`) không tiêu số nào.

### 3.5 Xoá hẳn: `SiteUserAbsent.Apply` và `userPurge` (dòng 545 đến 588)

`Apply`: tìm user; nếu user đã không còn thì chỉ xoá file crontab mồ côi (site xoá bằng bản cũ) rồi xong. Nếu còn thì `userPurge(ctx, sys, l, e.uid)` rồi `userDel`. UID lấy từ `getent` (`e.uid`), không tính lại.

`userPurge` bốn việc, theo thứ tự này, và mỗi thứ tự có lý do:

```go
if err := cageCrontabGone(ctx, sys, l); err != nil { return err }   // 1
if err := userKill(ctx, sys, l.User, uid); err != nil { return err } // 2
for _, d := range userTmpDirs {                                      // 3
	if err := userTmpClean(ctx, sys, d, uid); err != nil { return err }
}
// ... rồi userDel(...)                                              // 4
```

1. Crontab trước (`crontab -r -u <user>`, hàm `cageCrontabGone` ở `internal/steps/cage.go` dòng 1195). Crontab gắn với TÊN user, mà tên `tp_<slug>` sinh từ domain: tạo lại site cùng domain thì crontab cũ sống lại dưới user mới. Gỡ trước khi giết để cron không sinh tiến trình mới trong lúc đang giết.
2. Giết tiến trình (`userKill`, dòng 591). Một vòng: `kill -KILL -1` chạy dưới chính user đó (giết mọi tiến trình cùng UID trong một lượt kernel), rồi `pkill -KILL -U <uid>` (UID thật) và `pkill -KILL -u <uid>` (UID hiệu lực, mục 4.3), rồi chờ 100 ms và hỏi lại bằng `pgrep`. Lặp tới khi `pgrep` không thấy gì, tối đa `userKillWait` = 5 giây; quá hạn thì lỗi, không bỏ qua.
3. Xoá file của UID trong `/tmp`, `/var/tmp`, `/dev/shm` (`userTmpClean`, dòng 646): `find <dir> -xdev -uid N ! -type d -delete`, rồi thư mục rỗng của UID bằng `find ... -type d -empty -delete`. `-xdev` không sang phân vùng khác; `find` không đi theo symlink; symlink bị xoá chính nó, không xoá thứ nó trỏ tới. `find` có thể thoát khác 0 chỉ vì một file tự biến mất giữa lúc duyệt (`/tmp` luôn có file vào ra), nên khi xoá lỗi thì hàm hỏi lại bằng `userFindLeft` và chỉ báo lỗi khi còn file của UID.
4. Cuối cùng `userDel` (`userdel` không có `-r`, không có `-f`). Mã thoát 8 là "còn tiến trình": bản vá hiếm khi tới đây, vì bước 2 đã giết rồi.

Một chặn an toàn: `userPurge` từ chối UID 0 (dòng 573). Nếu `getent` trả lạ thì không bao giờ giết hay xoá thứ của root.

Vì sao dọn nằm trong `SiteUserAbsent` mà không tách thành Step riêng (`docs/thay-doi/M28.md` mục 43): Step riêng thì không có `Check` đúng khi user còn, vì cần UID của user mà user có thể đã mất. Gộp chung thì UID luôn lấy được ngay trước khi xoá.

## 4. Kiến thức nền

### 4.1 UID và GID

Linux không gắn quyền với tên mà với một số nguyên: UID (số của user) và GID (số của nhóm). Tên như `tp_x1_example_com_450f87` chỉ có trong `/etc/passwd`, một bảng "số sang tên". Mỗi file ghi chủ là số, không phải tên. `ls -l` tra bảng để in tên; `ls -ln` in số thẳng.

Hệ quả cần nhớ cho F1: xoá user chỉ xoá dòng trong bảng; file vẫn mang số cũ. Nếu có ai tạo user mới và gán đúng số đó, mọi file mang số ấy tự thành của người mới. Chỗ trong mã: dòng `ls -l` ở mục 2.1, tên chủ file đổi từ số sang `tp_x2_...`.

Tự nhìn trên máy ảo (chưa chạy trong phiên viết):

```bash
# trong máy ảo
id tp_x2_example_com_351da2          # uid=65541(...) gid=65541(...)
stat -c '%u %U %g %G' /var/www/x2.example.com
getent passwd 65541                  # tra ngược từ số ra tên
```

(Đổi tên user và domain theo máy bạn; liệt kê các site bằng `tpan site list`.)

### 4.2 Các dải UID và vì sao chọn 65536 đến 99999

Linux chia dải số UID theo thói quen, và Ubuntu 24.04 theo (nguồn trong comment mã, dòng 107 đến 116: `systemd.io/UIDS-GIDS` và `/etc/login.defs`):

| Dải | Ai dùng |
|---|---|
| 0 | root |
| 1 đến 999 | tài khoản hệ thống (gói cài bằng `adduser --system`, và `useradd --system`) |
| 1000 đến 60000 | người thật |
| 60001 đến 60577 | systemd-homed |
| 61184 đến 65519 | `DynamicUser=` của systemd (tài khoản tạm của dịch vụ) |
| 65534 | `nobody` |
| 65535 | giá trị "-1" của số 16 bit; không dùng |
| 100000 trở lên | dải UID phụ (`/etc/subuid`) cấp cho người thật chạy container không cần root |

Dải 65536 đến 99999 nằm giữa "mọi thứ đã có chủ" và "dải UID phụ". Không dưới 65536 vì dưới đó mỗi dải đã có chủ khác. Không từ 100000 vì nếu UID site rơi vào dải UID phụ của một người dùng, thì root bên trong container của người đó lại chính là user site, tức một người dùng khác có quyền của site.

Tự nhìn (chưa chạy trong phiên viết): `grep -E 'UID_MIN|UID_MAX|SYS_UID|SUB_UID' /etc/login.defs`; `awk -F: '$3 >= 65536' /etc/passwd` liệt kê user trong dải của tpan.

### 4.3 Setuid, UID thật và UID hiệu lực

File có bit setuid (hiện chữ `s` ở vị trí quyền thực thi của chủ: `-rwsr-xr-x`) có luật: ai chạy file đó, tiến trình chạy ra mang UID HIỆU LỰC (effective) là UID của chủ file, không phải của người chạy. UID thật (real) vẫn là của người chạy. `passwd` dùng cơ chế này để người thường sửa được `/etc/shadow`.

Ở đây: site x1 sao chép chương trình vào `/var/tmp` rồi đặt bit setuid. Ở bản chưa vá, khi UID đó thành của x2, bất cứ ai chạy file ấy thành x2. Trong thực tế thứ để lại là một shell, không phải `id` (script dùng `id` vì vô hại); và x2 đọc được `wp-config.php` của chính nó, nên người chạy file cũng đọc được (đây là điều KE-HOACH mục 6.28 viết).

Vì sao `/var/tmp`, `/tmp`, `/dev/shm`: ba thư mục này ai cũng ghi được (quyền 1777, bit "sticky"), nên user của site luôn tạo được file ở đó dù thư mục site bị khoá chặt. Đó là ba nơi bản vá dọn (`userTmpDirs`).

Vì sao giết cả `-U` lẫn `-u` (`userPgrep`, `userPkill`): một người chạy file setuid của site tạo ra tiến trình có UID hiệu lực là của site mà UID thật là của người đó. Chỉ `pkill -U` sẽ sót nó.

Tự nhìn (chưa chạy trong phiên viết):

```bash
# máy ảo, root
cp /usr/bin/id /tmp/thu-id && chmod 4755 /tmp/thu-id
ls -l /tmp/thu-id                    # có chữ s
runuser -u nobody -- /tmp/thu-id     # kỳ vọng: uid=65534 nhưng euid=0 (UID hiệu lực là của chủ file, root)
rm /tmp/thu-id
```

(Mục đích là thấy `euid` khác `uid`. Output ở dòng kỳ vọng là mình suy từ cách setuid hoạt động, chưa chạy; nếu `/tmp` gắn `nosuid` thì bit bị bỏ qua. Chỉ chạy trong máy ảo, không chạy trên VPS thật.)

### 4.4 Vì sao `useradd --system` cấp lại UID

Cờ `--system` bảo `useradd` lấy UID trong dải hệ thống (đã nói trong KE-HOACH mục 6.28: UID trống CAO NHẤT của dải 100 đến 999). UID của user vừa xoá lại trở thành "trống cao nhất", nên user kế tiếp nhận ngay nó. Trong log chưa vá: x1 = 993, x2 = 993; x3 = 992, ngay dưới.

GID thì cùng chuyện. `useradd --user-group` tạo nhóm riêng cùng tên; theo chú thích trong mã (dòng 139 đến 143, đọc từ mã shadow 4.13 `find_new_gid`, `check_gid`), nhóm đó chỉ được mang GID bằng UID khi số này nằm trong dải hệ thống. Ngoài dải, `useradd` lặng lẽ lấy GID trống cao nhất, tức dùng lại GID cũ. Đây là lý do mã gọi `groupadd --gid N` riêng rồi `useradd --gid N`, không dùng `--user-group`.

Chưa chạy trong phiên viết: để thấy hành vi cũ trên máy ảo sạch, `useradd --system thu1; id thu1; userdel thu1; useradd --system thu2; id thu2` (hai số bằng nhau).

### 4.5 Một interface nhỏ trong Go (`UIDReserver`)

`SiteUser.UIDs` có kiểu `UIDReserver`, interface một hàm (`internal/steps/site_user.go` dòng 130). `*store.Store` có hàm cùng chữ ký nên tự thoả, không khai báo "implements". Lợi ích: test của `steps` truyền một giá trị giả có hàm đó, không cần SQLite. Chỗ khác trong repo dùng cùng cách: `system.System` (mọi Step nhận nó chứ không gọi `os/exec` thẳng).

## 5. Cách khác đã cân nhắc

Chỉ ghi những gì có trong `docs/thay-doi/M28.md` mục 43, KE-HOACH mục 6.28 hay chú thích trong mã.

**Giữ `useradd --system` và chỉ dọn file sau khi xoá.** Không cấp lại UID loại cả nhóm lỗ cùng lúc: dù sót dấu vết nào (kể cả chỗ mình không nghĩ tới), nó mang một số không ai nhận lại, nên không thành của site mới. Chỉ dọn thì mọi chỗ sót đều thành lỗ. Dọn vẫn làm, nhưng là lớp phụ (mục 43 ghi chung cả hai; lý do bác riêng cách "chỉ dọn" mình suy từ đó, không phải câu chữ của mục).

**Dải UID: dưới 1000 (để nguyên dải hệ thống), 1000 trở lên, hay 65536 trở lên.** Dưới 1000: số có hạn (900), và `useradd --system` của gói khác cũng lấy ở đó. 1000 đến 60000: dải người thật, lẫn với tài khoản đăng nhập. 100000 trở lên: dải UID phụ của container. Chọn 65536 đến 99999 (mục 4.2).

**Lưu "số lớn nhất từng cấp" trong `tpan.db` hay quét `/etc/passwd`.** Quét `/etc/passwd` không nhớ được số của user đã xoá, nên chính là cái cần tránh. Chọn một dòng `settings` (`site_uid_max`) và ghi trước khi chạy lệnh. Không dùng bảng mới: một con số một dòng là đủ (chú thích `site_uid.go` dòng 10).

**Dọn trong Step riêng hay trong `SiteUserAbsent`.** Chọn gộp: Step riêng không có `Check` đúng khi user còn (mục 43). Gộp cũng giữ thứ tự cứng "dọn rồi mới `userdel`".

**Hàng đợi `at` không dọn.** Chú thích `ponytail:` trong mã (dòng 432 đến 434): Ubuntu server không cài sẵn `at`, và `atd` chạy job theo chủ của file job, mà UID đó không bao giờ được cấp lại. Nếu cần: `atq` rồi `atrm` các job của user site. Mình chưa kiểm trên máy ảo xem gói `at` có cài sẵn hay không.

**`NoNewPrivileges` cho PHP-FPM.** Phần này của bản rà soát được để sau (mục 43): nó đổi cấu hình PHP-FPM của site đang chạy, nên cần một e2e nâng cấp riêng.

## Đáp án

1. UID là số lưu trong inode của file, không phải tên. `ls -l` tra `/etc/passwd` để in tên. Lúc x1 còn, số 993 tra ra tên của x1; x1 xoá thì không tra ra (`ls -n` in số); x2 tạo ra và nhận số 993 thì tra ra tên của x2. Không có `chown` nào.
2. File có bit setuid chạy với UID hiệu lực là của chủ file, bất kể ai chạy. Nếu chủ file thành x2, ai chạy file đó (kể cả site hay user khác) thành x2 và đọc được những gì x2 đọc được (ví dụ `wp-config.php` của x2, theo KE-HOACH). File thường chỉ để lộ nội dung.
3. `--system` lấy UID trống cao nhất của dải hệ thống; UID vừa xoá hẳn là số trống cao nhất. Trong log chưa vá x1 và x2 cùng uid 993 (và cùng gid 984); x3 nhận 992, ngay dưới.
4. Python có sẵn trên máy ảo (script `chung2.sh` dùng sqlite3 của nó): `python3 -c "import sqlite3; print(sqlite3.connect('/var/lib/tpan/tpan.db').execute(\"select value from settings where key='site_uid_max'\").fetchall())"`. Giá trị phải bằng UID lớn nhất từng cấp (hoặc lớn hơn nếu có số bị bỏ phí vì `useradd` lỗi), tức không nhỏ hơn UID của site tạo gần nhất. Chưa chạy trong phiên viết.
5. Dưới 65536 mỗi dải đã có chủ (hệ thống, người thật, systemd homed, `DynamicUser=`, `nobody`). Từ 100000 là dải UID phụ của container không root, nên UID site ở đó thì root của container người khác là user site. 65536 đến 99999 là khoảng trống giữa hai thứ đó, 34464 số.
6. `id -u <user site 1>` trước khi xoá, ghi lại; sau khi tạo site 3, `id -u <user site 3>` phải lớn hơn. Hoặc `getent passwd <số cũ>` trống rỗng sau khi tạo site 3 (log bản vá có đúng dòng "getent passwd 65540: ''"). Chưa chạy trong phiên viết.
7. Nếu `useradd` xong mà tiến trình chết trước khi ghi số, số có thể cấp lại. Ghi trước thì tệ nhất là bỏ phí một số. Khi `useradd` lỗi, mã chạy `groupdel` để không để nhóm mồ côi; lần chạy lại lấy số mới (dòng 365 đến 369 trong `site_user.go`).
8. Theo chú thích trong mã (đọc từ shadow 4.13): với `--system`, nhóm tạo bởi `--user-group` chỉ mang GID bằng UID khi số nằm trong dải hệ thống; ngoài dải nó lấy GID trống cao nhất, tức dùng lại GID của site đã xoá. Tách `groupadd --gid` đảm bảo GID đúng bằng số đã cấp (log bản vá: 65541 và 65541).
9. Crontab, tiến trình, file ở `/tmp`, `/var/tmp`, `/dev/shm`, rồi `userdel`. Crontab trước vì nếu giết tiến trình trước thì cron có thể sinh tiến trình mới từ crontab giữa lúc đang giết; và crontab gắn với tên user, nên cũng là thứ sống lại khi tạo lại site cùng domain.
10. UID dưới 1000: site tạo trước bản này giữ UID cũ (`SiteUser.Check` chỉ xét tên, home, shell). Xoá hẳn một site như vậy thì UID đó vẫn thành "trống cao nhất" cho lần `useradd --system` của một gói khác, nhưng các dấu vết đã bị dọn nên không còn gì đi theo. `at`: Ubuntu server không cài sẵn `at`, `atd` chạy job theo chủ của file job, mà UID đó từ nay không bao giờ được cấp lại; nếu cần thì `atq`, `atrm` (comment `ponytail:`). `NoNewPrivileges`: chưa làm vì nó đổi cấu hình PHP-FPM của site đang chạy nên cần một e2e nâng cấp riêng; mục 43 ghi là để sau.
